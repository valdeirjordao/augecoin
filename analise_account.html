O módulo account.rs define a estrutura de dados mais fundamental da blockchain AugeCoin: a Account. Inspirada no modelo PascalCoin, cada conta é um registro imutável numerado sequencialmente que armazena saldo, chaves criptográficas híbridas (Ed25519 + ML-DSA-65), metadados e um contador anti-replay (n_operation).

Princípio fundamental: Toda conta AugeCoin é identificada por um u64 único e imutável. O número da conta nunca muda — apenas o dono (chave) pode ser alterado via operações ChangeKey.

2. Estrutura da Account

pub struct Account {
    pub account_number: u64,                       // Número sequencial único (PASA)
    pub account_info:   AccountInfo,                   // Estado, chave, preço, bloqueio
    pub balance:        u64,                       // Saldo em augesat (menor unidade)
    pub updated_on_block_passive_mode: u64,  // Último bloco de atualização (passivo)
    pub updated_on_block_active_mode:  u64,  // Último bloco de atualização (ativo)
    pub n_operation:   u64,                       // Contador anti-replay
    pub name:          Option<String>,           // Nome PASA (ex: "augecoin")
    pub account_type:  u16,                       // Tipo da conta (definido pelo usuário)
    pub account_data:  Vec<u8>,                   // Dados on-chain (max 32 bytes)
    pub account_seal:  Vec<u8>,                   // Selo criptográfico (max 32 bytes)
}

2.1 Detalhamento dos Campos

CampoTipoTamanho serializadoDescrição
account_number u64 8 bytes Identificador único. Contas são numeradas sequencialmente pelo protocolo. Números de conta nunca são reutilizados após RecoverFounds — a conta é zerada mas mantém o número.
balance u64 8 bytes Saldo em augesat (1 AUGE = 100.000.000 augesat). Todas as operações aritméticas usam checked_add/checked_sub para prevenir overflow/underflow.
n_operation u64 8 bytes Contador anti-replay. Incrementado a cada operação confirmada que usa esta conta como sender. O nó validador verifica que o n_operation da operação casa com o da conta — impedindo replay de transações.
name Option<String> 2 + len (max 64) Nome PASA opcional. Segue o modelo PascalCoin: qualquer conta pode ter um nome único legível (ex: "alice", "exchange"). Nome vazio é representado como None (serializado como 0xFFFF).
account_type u16 2 bytes Tipo definido pelo usuário (0 = padrão). Permite classificação de contas (ex: contrato, multisig, etc.).
account_data Vec<u8> 2 + len (max 32) Payload de dados on-chain. Limitado a 32 bytes (CT_MAX_ACCOUNT_DATA). Pode armazenar hashes, referências ou metadados arbitrários.
account_seal Vec<u8> 2 + len (max 32) Selo criptográfico. Utilizado para operações de troca atômica (Atomic Swap).
updated_on_block_passive_mode u64 8 bytes Bloco da última atualização em modo passivo (a conta recebeu fundos).
updated_on_block_active_mode u64 8 bytes Bloco da última atualização em modo ativo (a conta enviou fundos ou foi modificada).

3. AccountState — Máquina de Estados

pub enum AccountState {
    Unknown              = 0,   // Estado desconhecido/inicial
    Normal               = 1,   // Conta normal (operável)
    ForSale              = 2,   // Conta à venda (listada no mercado PASA)
    ForAtomicAccountSwap = 3,   // Em processo de swap atômico de conta
    ForAtomicCoinSwap    = 4,   // Em processo de swap atômico de moeda
}

3.1 Transições de Estado

                    ListAccountForSale
  Normal ──────────────────────────────────► ForSale
    ▲                                           │
    │          DelistAccount / BuyAccount       │
    └───────────────────────────────────────────┘

  Normal ──► ForAtomicAccountSwap ──► (swap concluído) ──► Normal
  Normal ──► ForAtomicCoinSwap    ──► (swap concluído) ──► Normal

3.2 Regras

  • Normal: Conta totalmente operável. Pode enviar/receber transações.
  • ForSale: Conta anunciada para venda. price define o valor, account_to_pay o destinatário, locked_until_block o bloqueio temporal.
  • ForAtomicAccountSwap: Conta bloqueada em protocolo de troca atômica de conta. Usa hashed_secret para HTLC.
  • ForAtomicCoinSwap: Similar, mas para troca de moedas/coins.
Atenção: Contas em estado ForSale não podem enviar operações. Qualquer tentativa de usar uma conta à venda como sender será rejeitada na validação.

5. HybridAccountKey — Criptografia Híbrida

pub const ED25519_PK_LEN: usize = 32;
pub const ML_DSA_65_PK_LEN: usize = 1952;

pub struct HybridAccountKey {
    pub ed25519_public_key: [u8; 32],         // Curva elíptica clássica
    pub ml_dsa_public_key:  [u8; 1952],       // Pós-quântica ML-DSA-65
}

5.1 Motivação

A AugeCoin utiliza um esquema de dupla assinatura: cada conta possui simultaneamente uma chave Ed25519 (rápida, amplamente suportada) e uma chave ML-DSA-65 (resistente a ataques quânticos). Ambas devem ser válidas para que uma operação seja aceita.

5.2 Métodos

MétodoDescrição
empty()Cria chave zerada (todos os bytes = 0). Usada para contas recém-criadas sem dono definido.
is_empty()Verifica se ambas as chaves são zero. Retorna true para contas não reivindicadas.
Observação: O tamanho total de uma HybridAccountKey é 1.984 bytes. O ML-DSA-65 (FIPS 204) produz chaves públicas de 1.952 bytes e assinaturas de 3.309 bytes — isso impacta diretamente o tamanho das transações e o throughput da rede.

7.2 Representação de String Opcional

O campo name usa um esquema especial:

  • None → serializado como 0xFFFF (2 bytes)
  • Some(s) → [len: u16 BE][bytes UTF-8]
  • Nome limitado a 64 bytes (validado na desserialização, não na serialização)
Crítico para consenso: A função to_bytes() é a base do hash() que por sua vez alimenta o SafeBox. Qualquer não-determinismo (ordem diferente, endianness, padding) quebraria a consistência entre nós.

9. Criação de Contas (PASA)

Modelo PASA (PascalCoin Account): Contas são criadas automaticamente pelo protocolo a cada bloco, em lotes de CT_ACCOUNTS_PER_BLOCK = 5. O número da conta = block_number * 5 + offset.

9.1 Processo de Criação

Bloco N (leader_id = L)
┌─────────────────────────────────────────┐
│  execute_block()                        │
│    │                                    │
│    ├── Fase 1-2: validação + execução   │
│    ├── Fase 3: distribuir reward+fees   │
│    │                                    │
│    └── Fase 4: criar novas contas       │
│         │                               │
│         start = N * 5                   │
│         │                               │
│         for i in 0..5:                  │
│           new_num = start + i           │
│           Account::new(                 │
│             new_num,                    │
│             [0u8; 32],  ← chave zerada │
│             [0u8; 1952],← "            │
│             block_number                │
│           )                             │
│           account_key = leader's key    │
│           balance = 0                   │
└─────────────────────────────────────────┘

9.2 Características

  • Contas nascem zeradas: balance = 0, n_operation = 0.
  • Chave do líder: A nova conta recebe a chave do validador que produziu o bloco. O líder pode posteriormente transferir a conta via ChangeKey ou vendê-la via ListAccountForSale.
  • Números previsíveis: Qualquer nó pode calcular quais contas existirão em um dado bloco.

9.3 Recuperação de Contas Abandonadas

Contas com saldo zero que foram abandonadas podem ser recuperadas via operação RecoverFounds:

// execution.rs - OperationPayload::RecoverFounds
if acc.balance > 0 {
    return Err(...);  // Não pode recuperar conta com saldo
}
acc.balance = 0;
acc.n_operation = 0;
acc.name = None;
acc.account_type = 0;
acc.account_data = Vec::new();
acc.account_seal = Vec::new();
acc.account_info = AccountInfo::default();  // Reseta chaves
Nota: RecoverFounds zera completamente a conta e reseta suas chaves, mas não altera o account_number. O número da conta permanece o mesmo — apenas o dono muda.

10. Considerações de Segurança

10.1 Prevenção de Overflow

OperaçãoMétodoProteção
Créditochecked_add(amount)Retorna BalanceOverflow se saldo > u64::MAX
Débitochecked_sub(amount)Retorna InsufficientBalance se saldo < amount
n_operationsaturating_add(1)Satura em u64::MAX (embora na prática nunca alcance)

10.2 Anti-Replay

Toda operação que envolve um sender inclui n_operation. O execution layer verifica:

// execution.rs
if sender.n_operation != acc.n_operation {
    return Err(ExecutionError::OperationFailed {
        sender: sender.account,
        reason: "invalid n_operation: expected {acc}, got {op}",
    });
}
acc.increment_n_operation();

Isso garante que cada operação de uma conta seja única e imune a replay.

10.3 Bloqueio Temporal

Contas podem ser bloqueadas até um bloco específico (locked_until_block). O método is_locked() usa comparação >= — a conta só é liberada quando current_block > locked_until_block.

10.4 Validação de Dados

  • account_data limitado a 32 bytes (CT_MAX_ACCOUNT_DATA)
  • account_seal limitado a 32 bytes
  • name validado como UTF-8 válido
  • Estado da conta validado contra enum (valores 0-4)

10.5 Hash Determinístico

O hash da conta usa blake3-512 sobre sua representação serializada. Qualquer nó que execute as mesmas operações na mesma ordem produzirá exatamente o mesmo hash — fundamental para o consenso do SafeBox.

13. Conclusão & Recomendações

13.1 Pontos Fortes

  • Serialização determinística — ordem fixa big-endian, sem ambiguidade
  • Proteção contra overflow — checked_add/checked_sub em todas as operações
  • Anti-replay robusto — n_operation validado em toda operação
  • Criptografia híbrida — resistente a ataques clássicos e quânticos
  • Modelo PASA — contas numeradas, previsíveis, sem colisão
  • Hash blake3-512 — rápido e determinístico para integridade do SafeBox

13.2 Pontos de Atenção

  • Tamanho da chave ML-DSA-65 (1.952 bytes) — cada conta ocupa no mínimo ~2 KB. Com milhões de contas, o SafeBox pode crescer rapidamente.
  • Assinaturas ML-DSA-65 (3.309 bytes) — transações são pesadas. O throughput da rede é limitado pelo tamanho das operações.
  • RecoverFounds não remove a conta — apenas zera. O número nunca é reutilizado, o que pode levar a fragmentação do espaço de números.
  • Contas sem dono (chave zerada) — contas recém-criadas têm chave do líder, mas se o líder nunca fizer ChangeKey, a conta fica permanentemente associada a ele.

13.3 Recomendações

  1. Compressão de chaves: Considerar compressão da chave ML-DSA no SafeBox para reduzir armazenamento.
  2. Limpeza de contas zeradas: Avaliar remoção de contas com balance=0 e n_operation=0 que nunca foram usadas.
  3. Índices secundários: Para busca por nome ou chave pública, considerar índices auxiliares fora do consenso.
