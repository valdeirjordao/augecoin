1 — Visão Geral

Resumo Executivo

AUGECOIN é uma blockchain Proof of Authority construída em Rust, com:

  • Assinaturas híbridas: Ed25519 + CRYSTALS-Dilithium (pós-quântico desde o gênesis)
  • BLAKE3-512 hashing (modo XOF, 512 bits)
  • SafeBox — modelo de estado incremental com snapshots determinísticos
  • Consenso PoA — quórum 2/3+1, líder round-robin
  • Contas nativas numeradas (AUGEID) com marketplace, doações e resolução de nomes
  • Suprimento total: 750.000.000 AUGE (75 trilhões de augesat), emitido em 50 anos

3 — SafeBox

CAPÍTULO MAIS IMPORTANTE

Estrutura

SafeBox {
  header: SafeBoxHeader {
    protocol, start_block, end_block,
    blocks_count, safe_box_hash
  }
  accounts: BTreeMap<u64, Account>    // ordenado por número
  name_index: BTreeMap<String, u64>  // nome → número
}

Ciclo de Vida do AUGEID

Unknown → (emissão do bloco) → Reserved → (venda/doação) → Owned → Normal
                                       ↘ GiftPending (aguardando aceite)
EstadoDescrição
ReservedEmitido ao líder; sem chave; não envia/recebe AUGE
OwnedTem proprietário (account_key, n_operation=0)
ForSaleAnunciado no marketplace (sale_index)
GiftPendingDoação pendente (gift_index)
NormalConta operacional

Hash de Consenso

compute_safe_box_hash() = raiz Merkle (blake3_512) sobre:

  1. accounts.values().map(|a| a.hash()) — folha por conta
  2. name_index — blake3(name || number) por entrada

SafeBox vazio → [0u8; 64]. O hash é gravado no header do bloco e realimentado no seguinte.

Persistência Incremental

execute_block (por bloco)
  └─ commit_block_atomic(&modified, block, validator_set_bytes)
        ├─ WriteBatch: put_account + put_block + put_height + put_validator_set
        ├─ atualiza SafeboxCache (O(k))
        └─ snapshot completo periódico

Índices Residentes

pubkey_indexpubkey → refcountdetecção de chave duplicada

4 — Consenso

Proof of Authority (PoA)

ParâmetroValor
ModeloPoA com líder rotativo round-robin
Quórum2/3 + 1 → 3 assinaturas válidas de 4
Líderactive[(H+1+round) % len]
Timeout120s (2× block time) → view-change
EquivocationProva on-chain com duas assinaturas conflitantes

Máquina de Estados da Rodada

Propose → Collect → Commit
   │         │         │
   │    add_signature  │
   │    acumula sigs   │
   └─── timeout ───→ view_change (próximo líder)
FaseDescrição
ProposeLíder constrói bloco com initial_safe_box_hash e assina
Collectadd_signature acumula assinaturas dos demais validadores
Committry_commit quando assinaturas ≥ quórum
Timeoutcheck_timeout dispara view_change

Verificação de Quórum

3 assinaturas válidas de 4 finalizam um bloco. Generalizado: quorum_threshold(n) = ⌈2n/3⌉ + 1.

Assinaturas de validadores fora do ValidatorSet ativo não contam para o quórum.

Verificação de Bloco

  1. Rejeita timestamp futuro além de CT_MAX_FUTURE_BLOCK_TIMESTAMP_SECONDS
  2. Verifica assinatura do líder (Ed25519) sobre block.hash()
  3. Verifica assinaturas de quórum dos validadores ativos
  4. Valida operations_hash == Merkle das operações do bloco

5 — Storage

RocksDB Column Families

CFConteúdoAcesso
accountsAugeAccount serializadoR/W por bloco
blocksHeaders + bodiesWrite once, read often
tx_indextx hash → blocoWrite once, index lookup
validator_setValidadores ativosWrite per governance
equivocation_proofsEquivocationProofWrite on detection

Atomicidade (WriteBatch)

commit_block_atomic:
  ├─ put_account(contas modificadas)
  ├─ put_block(bloco)
  ├─ put_height(altura)
  ├─ put_validator_set(validadores)
  └─ flush(WAL)

Solução WAL Growth

O crescimento do Write-Ahead Log foi resolvido com:

  1. set_max_total_wal_size para limitar uso de disco
  2. Compactação periódica após snapshots de checkpoint
  3. set_keep_log_num para controle de retenção

Snapshots e Checkpoints

Intervalo: SAFEBOX_SNAPSHOT_INTERVAL_DEV = 100 / _MAINNET = 1000.

flush_safebox_snapshot() força snapshot (shutdown/export/recovery).

6 — Rede

libp2p + Noise

Criptografia obrigatória via Noise Protocol — nenhuma conexão sem criptografia é aceita.

libp2p Transport
  ├─ Noise     (encryption)
  ├─ TCP       (transport)
  └─ Yamux     (multiplexing)

Gossipsub

TópicoConteúdoPropagação
txTransações pendentesFlood para todos os peers
blockBlocos finalizadosFlood para todos os peers
consensusMensagens de consensoMesh apenas validadores

Protocolo de Sync

Novo Nó
  │
  ├─ Conecta aos bootnodes (handshake Noise)
  ├─ Solicita checkpoint mais recente
  │     └─ Restaura SafeBox do checkpoint
  ├─ Solicita blocos restantes
  │     └─ Executa cada bloco (verifica quórum)
  ├─ Entra no mesh gossipsub ao vivo
  └─ Participa do consenso (se validador)

Descoberta de Peers

Lista estática de bootnodes (configurável). Sem Kademlia DHT — escolha pela simplicidade e auditabilidade em rede de 4 validadores.

9 — AUGEID

Ciclo de Vida Completo

Bloco N
  │
  ↓
Reserved (10 AUGEIDs por bloco, todos ao líder)
  │
  ├──→ ForSale (listado no marketplace)
  │       └──→ Owned (comprado)
  │
  ├──→ GiftPending (doação iniciada)
  │       └──→ Owned (doação aceita)
  │
  └──→ Owned (ativação direta)
          └──→ Normal (conta operacional)
EstadoDescriçãoSaldoEnvia
ReservedEmitido ao líder do bloco—❌
OwnedTem proprietário, sem chave definitiva—❌
ForSaleListado no marketplace—❌
GiftPendingDoação aguardando aceite—❌
NormalConta operacional✅✅

Fórmula de Numeração

AUGEID = bloco × 10 + offset (0..9)

Cada bloco emite exatamente 10 AUGEIDs, todos Reserved e pertencentes ao líder.

Por que AUGEID é um Ativo

Escassez

Apenas 10 por bloco, cronograma fixo

Negociabilidade

Podem ser compradas, vendidas, doadas

Identidade

Contas nomeadas (resolve_name)

Especulação

Números anteriores/menores podem ter prêmio

Sem expiração

Contas persistem para sempre

11 — Segurança

Criptografia

PrimitivaAlgoritmoFinalidade
AssinaturaEd25519 + Dilithium (dual)Assinatura de tx/bloco
HashingBLAKE3-512 (XOF)State root, hash do bloco
DerivaçãoHKDF-SHA3-512HD wallet
EndereçoBech32mEndereços legíveis

Proteção contra Replay

  • op_sequence por conta: monotonicamente crescente
  • Mesma operação não pode ser submetida duas vezes
  • Mempool rejeita sequências desatualizadas

Superfícies de Ataque

1. RPC HTTP

Porta configurável, exposta na rede. Mitigado com TLS obrigatório.

2. libp2p / Rede

Gossipsub + bootnodes. Mitigado com Noise encryption.

3. Assinaturas

Validação Ed25519+Dilithium. Dual-sign desde o gênesis.

4. Serialização

Blocos/tx malformados. Mitigado com validação na desserialização.

5. Faucet

Distribuição de tokens. Rate limiting implementado.

6. Chaves

Gerenciamento de chaves dos validadores. Nunca em config versionado.

Limitações Conhecidas

  • Sem atomic swaps
  • Sem exclusão de blockchain
  • Sem recuperação de coins com chave perdida
  • Chave admin é single-key (não multisig)
