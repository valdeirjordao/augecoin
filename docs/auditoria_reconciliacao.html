Resumo Executivo: O código atual não implementa a AUGECOIN descrita no whitepaper. Ele implementa uma variante do PascalCoin traduzida para Rust, com modelo de emissão halving-style, 20% de taxa de desenvolvedor, 5 contas por bloco, marketplace de contas (ForSale/BuyAccount), e cabeçalhos de bloco tipo PascalCoin. O arquivo transaction.rs (SPEC-compliant) existe mas não é usado por nenhum outro módulo. O checklist PRE_MAINNET_CHECKLIST.md afirma incorretamente que a SPEC e a implementação estão alinhadas.

A função block_reward() implementa divisão sucessiva por 2 a cada CT_NEW_LINE_REWARD_DECREASE = 210.240 blocos, com piso de CT_MIN_REWARD_AUGESAT. Esse modelo nunca chega a zero — a emissão é perpétua, violando a SPEC que exige 0 após o bloco 26.298.000.

2. Supply CRÍTICO

As constantes em emission.rs :7-8:

pub const TOTAL_SUPPLY_AUGE: u64 = 750_000_000;
pub const TOTAL_SUPPLY_AUGESAT: u64 = TOTAL_SUPPLY_AUGE.saturating_mul(ONE_AUGE);
Nenhuma função de emissão usa essas constantes como constraint. O total de 750 milhões de AUGE nunca será atingido com precisão porque:
  • Halving a cada 210.240 blocos, começando em 1 AUGE (100M augesat), mínimo 0,1 AUGE (10M augesat)
  • Cada bloco emite entre 10M e 100M augesat — as contas não fecham para 75 quadrilhões exatos
  • Não existe o teste de propriedade que a SPEC exige (sum(block_reward(h)) == TOTAL_SUPPLY_AUGESAT)

O teste emission_total_supply.rs verifica apenas que a recompensa é monotonicamente decrescente, que nunca excede CT_FIRST_REWARD_AUGESAT e que não vai abaixo do mínimo — não verifica o total exato.

7. Recompensas dos Validadores CRÍTICO

Mesma divergência do item 3. O validador líder recebe apenas 80% da emissão (e 0% das taxas), em vez de 100% de ambos conforme a SPEC.

Fluxo real em execution.rs :90-188:

  1. reward = block_reward(block_number)
  2. dev_reward = reward * 20 / 100 → conta dev
  3. leader_reward = reward - dev_reward → líder
  4. total_fees → conta dev (não líder)

  • state_root.rs tem uma implementação de Merkle tree correta (compute_state_root() com BTreeMap)
  • execution.rs não usa compute_state_root() — usa SafeBox (safe_box.rs)
  • execute_block() retorna safe_box_hash, não state_root
  • O OperationBlockHeader contém proof_of_work (32 bytes) — conceito PascalCoin inexistente na SPEC AUGECOIN

RegraDescriçãoStatus

Rule 7 "Nada de tradução literal de código de terceiros. Nenhum código Object Pascal deve ser traduzido linha por linha." VIOLADA

Rule 1 "Proibido simular, placeholder, mock, dados fake." ✅ OK
Rule 2 — 20% de taxa de desenvolvedor. O código reserva 20% de toda emissão + 100% de todas as taxas para 5 contas de desenvolvedor (CT_DEVELOPER_ACCOUNT_START a CT_DEVELOPER_ACCOUNT_COUNT). Isso constitui uma taxa de desenvolvedor embutida no protocolo — explicitamente proibida.
Rule 7 — Tradução do PascalCoin. O sistema de operações (operation.rs), o modelo de conta com estados ForSale/BuyAccount (account.rs), o SafeBox (safe_box.rs), e o cabeçalho de bloco com proof_of_work (block.rs) são uma tradução direta do protocolo PascalCoin. O ADR-002 afirma que "nenhum código PascalCoin é traduzido linha a linha", mas a estrutura inteira da camada de execução é derivada dele.
Rule 9 — Hard fork silencioso de regras monetárias. O modelo de emissão halving perpétuo substitui o modelo determinístico de 50 anos com supply exato de 750 milhões. Nenhum ADR registra essa decisão.

PRE_MAINNET_CHECKLIST.md — Falsos Positivos

O checklist em docs/PRE_MAINNET_CHECKLIST.md afirma:

"Section 3 (Emission): Matches — block_reward() implementation verified by proptest"
Isso é falso. O proptest emission_total_supply NÃO verifica sum(block_reward(h)) == TOTAL_SUPPLY_AUGESAT — ele testa apenas monotonicidade, teto máximo e piso mínimo. O modelo de emissão no código é halving-style, não o determinístico da SPEC.
"Section 4 (Block production): Matches — new account auto-assigned to leader (ADR-005)"
Parcialmente falso. A atribuição ao líder está implementada, mas o código cria 5 contas por bloco (CT_ACCOUNTS_PER_BLOCK = 5), não 1 como manda a SPEC.

Conclusão

O código atual não é a implementação da AUGECOIN descrita no whitepaper. É uma fork do PascalCoin traduzida para Rust, com:

Emissão halving perpétua Nunca atinge 750M exatos 20% taxa de desenvolvedor 5 contas por bloco Marketplace de contas Bloco estilo PascalCoin proof_of_work no header SafeBox em vez de state_root

Caminhos para Correção

Opção A — Alinhar código ao Whitepaper:
  1. Reescrever emission.rs com o modelo determinístico da SPEC (base_reward + remainder, zero após TOTAL_EMISSION_BLOCKS)
  2. Remover developer_reward(), developer_account_for_block(), e contas de dev
  3. Reduzir CT_ACCOUNTS_PER_BLOCK para 1
  4. Substituir operation.rs por transaction.rs na engine de execução
  5. Alinhar block.rs com o BlockHeader da SPEC (prev_hash, state_root, tx_merkle_root, round_reward, new_account_number)
  6. Remover SafeBox e usar compute_state_root() em execute_block()
  7. Distribuir 100% da recompensa + 100% das taxas ao líder
  8. Implementar getValidatorEarnings no RPC
  9. Remover seeds do genesis.toml (usar variáveis de ambiente)
Opção B — Formalizar o modelo atual como regra oficial: Registrar um ADR explícito em DECISIONS.md declarando que o protocolo adota o modelo halving, 20% dev, 5 contas/bloco, e estrutura PascalCoin.
